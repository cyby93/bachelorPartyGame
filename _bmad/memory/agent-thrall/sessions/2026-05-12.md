# Session Log — 2026-05-12

## Task
Investigate four visual bugs in training grounds:
1. Projectile sprites frozen at spawn
2. Drain Life beam stays indefinitely
3. Bladestorm zone stays indefinitely
4. Consecration zone stays indefinitely

## Findings

### Bug 1 — Projectile sprites frozen at spawn position

**Not a container mounting issue.** `BaseRenderer.enter()` (line 56–57) correctly adds `_projectileContainer` to `layers.fx`. `layers.fx` is a child of `worldRoot`, which is the scaled world container. Z-order is fine.

**Not a `knownState` update issue.** `StateSerializer.buildDeltaState()` (line 160–172) always populates `projectiles` unconditionally. `HostGame.receiveState()` (line 296) assigns it when non-null.

**Root cause located — `ProjectileSprite.update()` logic at line 65:**
```js
if (this.container.position.x !== 0 || this.container.position.y !== 0) {
  // push trail point
}
this.container.position.set(newX, newY)  // line 92 — this runs correctly
```
The position IS being set. However: the sprite IS frozen visually. This means the issue is that `_syncProjectiles()` is correctly moving the sprite but the trail `_drawTrail()` call (after line 99) draws relative to `newX, newY` using `this._trailGfx` — a child of `container`, which is positioned at `(newX, newY)`. **The trail graphics use absolute positions but the Graphics child is in the parent's local space.** Inspect `_drawTrail` — if it calls `moveTo(point.x, point.y)` using trail history (which stores absolute container positions), those trail points are now relative to the container (wrong). The body sprite will appear at the right place but the trail smears back to origin.

Actually — more precisely — the BODY should move if line 92 runs. If the body itself appears frozen, then the update loop is not reaching `_syncProjectiles()`. The only other explanation: `TrainingGroundsRenderer` never calls `super.update()` or... wait, it doesn't override `update()`. `BaseRenderer.update()` is inherited and calls `_syncProjectiles()` directly. That chain is solid.

**Most likely actual freeze:** The server projectile `vx/vy` are correct but `_tickProjectiles` receives `dt` from `(now - lastTick) / 1000`. If `lastTick` was initialized wrong or if the training grounds tick rate has an issue, `dt` could be near zero causing effectively zero movement per tick. But the tick is shared with battle — unlikely.

**More likely:** `projectile_default` texture is not loading — `Assets.get('projectile_default')` at ProjectileSprite.js line 50 returns undefined/null, making `new Sprite(null)` which could render as a 0×0 invisible sprite. The `_trailGfx` Graphics would still draw but at the tiny default size. This would LOOK frozen/invisible. Check whether `projectile_default` exists in public/assets/sprites/.

### Bug 2 — Drain Life beam stays indefinitely

**Root cause confirmed: `p.beamTargetId` in `knownState.players` retains a stale non-null value.**

`_renderBeams()` (BaseRenderer.js line 225) draws a beam whenever `p.beamTargetId` is truthy and `_resolveBeamTarget()` returns a valid position. The beam disappears only when the server clears `p.beamTargetId` to null/undefined in the player DTO.

`HostGame.receiveState()` at line 268–289: player fields are merged with `Object.assign(p, d)`. So `beamTargetId` only gets cleared if the delta explicitly sends `beamTargetId: null`. If the server stops sending `beamTargetId` once channeling stops (omits the field rather than nulling it), `knownState` will retain the stale value.

This is a **server-side delta DTO bug**: when a channel ends (interrupted or completed), the player's `toDeltaDTO()` must explicitly include `beamTargetId: null`. If it just omits the field when not channeling, the client never clears it.

### Bug 3 — Bladestorm zone stays indefinitely
### Bug 4 — Consecration zone stays indefinitely

**Both share the same root cause: `knownState.aoeZones` is never cleared on scene transition.**

In `HostGame.switchScene()` (line 233–247), there is NO explicit clear of `knownState.aoeZones`, `knownState.projectiles`, `knownState.enemies`, etc. The only reset is `knownState.players = {}`.

**The stale zone flow:**
1. Player casts Consecration or Bladestorm in battle or bossFight
2. Zone is added to `skillSystem.activeZones` on server
3. Server-side `_clearCombatState()` does clear `skillSystem.activeZones = []` (line 894)
4. BUT: `_clearCombatState()` is NOT called when transitioning TO training grounds from the lobby path — it's called only via `_startCampaign()` (line 587), `_startLevel()` (line 611), and `_onHostStartTraining()` (line 557)
5. `_onHostStartTraining()` DOES call `_clearCombatState()` before `_changeScene('trainingGrounds')` — so the server zones ARE cleared
6. **But the client-side `knownState.aoeZones` still holds the old array from the previous battle scene**, because `switchScene()` doesn't reset it
7. The very first delta from training grounds sends `aoeZones: []` — but only IF the `buildDeltaState` runs after the scene change AND the client receives it. There's a race: `switchScene()` runs on the client when `SCENE_CHANGE` arrives. The next `STATE_DELTA` hasn't arrived yet. The renderer's first few `update()` frames read the stale `knownState.aoeZones` from the previous scene and render those old zones.

**This is the concrete bug**: `HostGame.switchScene()` does not reset `knownState.aoeZones` (or `knownState.projectiles`, `knownState.enemies`) before calling `activeRenderer.enter()`. The new renderer starts rendering stale data from the old scene for the duration of one server tick.

For zones specifically: `GroundEffectSystem.sync()` receives the stale zones on the first few frames, creates visuals for them, and then on the next delta (which sends `aoeZones: []`) removes them. **So the zones should only flicker briefly (50ms), not stay indefinitely** — unless the delta never sends `aoeZones: []`.

Wait — actually `buildDeltaState()` line 203 ALWAYS includes `aoeZones: gs.skillSystem.getZonesDTO()`. And `getZonesDTO()` returns `this.activeZones.map(...)` — after `_clearCombatState()` sets `activeZones = []`, this returns `[]`. So the first delta after training grounds starts WILL send `aoeZones: []`, clearing the client. The window is only 50ms.

**Unless**: the zones are being re-added in training grounds because players are casting Consecration/Bladestorm in training grounds, the zones expire normally on the server, but the server NEVER sends `aoeZones: []` because the `receiveState()` merge pattern is `if (delta.aoeZones != null)` — which is always true (it's always an array, possibly empty). So empty arrays DO clear it. This should work.

**Revised hypothesis:** The zone persists because `GroundEffectSystem._zones` map is NOT cleared between scene switches. The `VFXManager` is destroyed in `exit()` (line 88) and recreated in `enter()` (line 59). So `GroundEffectSystem` IS fresh every scene. That's correct.

**Most likely actual cause for persistent zones**: The server is NOT sending `aoeZones: []` after the zone expires. Look at `buildDeltaState()` — it calls `getZonesDTO()` which maps `activeZones`. If `activeZones` retains a zone past its `expiresAt` because `_tickZones()` only runs on battle/bossFight scenes (need to verify), then the zone lives forever server-side too, and `aoeZones` in every delta still contains it.

Check: does `skillSystem.tick()` get called for training grounds? GameServer.js line 1151 confirms YES: `if (this.scene === 'lobby' || this.scene === 'trainingGrounds') { skillSystem.tick(gs, dt) }`. And `tick()` calls `_tickZones()` (SkillSystem.js line 127). So zones DO expire. 

**The real issue must be Bladestorm specifically**: `_tickZones()` at line 1630–1633:
```js
if (zone.config.subtype === 'BLADESTORM') {
  const owner = gs.players.get(zone.ownerId)
  if (owner) owner.bladestormActive = false
}
```
The zone expires and is spliced out. But the client side zone visuals only clear when `sync([])` is called with no entry for that ID. If `aoeZones` delta arrives with an empty array, `GroundEffectSystem.sync([])` at line 47 — `activeIds` is empty, and the forEach at line 105 removes all zones. This is correct.

**Conclusion**: The persistent zone bug is most likely that zones created during a previous scene (battle → levelComplete → training grounds) are leaking through because `knownState.aoeZones` is not reset in `switchScene()`, AND the timing between SCENE_CHANGE and the first STATE_DELTA means the stale zones are rendered for 1-2 frames… but actually they would clear on the next delta. So if they "stay indefinitely" in Cyby's report, it may mean the Bladestorm/Consecration zone was cast IN training grounds and its own expiry logic has a bug, OR the zone in a previous scene never expired server-side before the scene changed.

## Recommended Fixes

### Fix 1: Reset stale state in `switchScene()` — HostGame.js
Add before `this.activeRenderer?.exit()`:
```js
// Clear per-scene state to avoid stale data leaking into new renderer
this.knownState.aoeZones   = []
this.knownState.projectiles = []
this.knownState.enemies    = []
this.knownState.tombstones = []
this.knownState.minions    = []
```

### Fix 2: Beam persistence — player DTO delta must explicitly null beamTargetId
In server `Player.toDeltaDTO()`, always include `beamTargetId: this.beamTargetId ?? null`. Never omit it when transitioning out of channeling.

### Fix 3: Projectile sprite invisible — verify `projectile_default` asset
Check that `public/assets/sprites/projectile_default.png` exists and is a valid PNG. If Assets.get() fails silently, Sprite gets a null texture and is invisible.
