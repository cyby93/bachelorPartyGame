# Session — 2026-05-14

## Work Done

### Fix 1: Projectile Trail Linger

**Problem:** `_syncProjectiles()` called `s.destroy()` the moment a projectile left server state (on hit). Trail geometry and particles vanished in a single frame.

**Solution:**
- Added `detach()` to `ProjectileSprite.js`: hides body, sets `_detached`/`_detachedAt`
- Added `updateDetached()`: ages out particles, fades `_trailGfx.alpha` over 400ms, returns `true` when fully gone
- `BaseRenderer._syncProjectiles()` now calls `s.detach()` and moves to `_dyingProjectiles` instead of destroying
- New `_tickDying(map, container)` helper handles the per-frame fade+cleanup loop
- Same pattern applied to boss fireballs via `_dyingBossFireballs`

### Fix 2: Tracked Heal Beams

**Problem:** Chain Heal and Regrowth used `_flashBeams` (static coordinates). When caster/target moved during the 400ms beam, the beam stayed pinned at spawn-time positions.

**Solution:**
- `targeted:hit` event only carries coordinates, not IDs — so ID-based tracking (like Death Grip) isn't possible without server changes
- New approach: `_findClosestSpriteContainer(x, y)` finds the nearest PlayerSprite or EnemySprite container at event-fire time (accurate within render interpolation tolerance)
- New `_trackedRefBeams` array stores `{ fromRef, toRef, ... }` — references to live Pixi Containers
- `_renderBeams()` reads `b.fromRef.x/.y` and `b.toRef.x/.y` each frame; guards with `.destroyed` check
- `_hitChainHeal` and `_hitRegrowth` now push to `_trackedRefBeams` with fallback to `_flashBeams` if lookup fails

### Fix 5: Moonfire beam — shrinking column

Replaced `_flashBeams` vertical line with a custom `OneShotEffectSystem.moonfireBeam(x, y)`.
Three nested rectangle columns (outer glow / main / bright core), all sharing `w = 9 * (1 - progress)` as half-width — the full column squeezes to zero width over 250ms. Both top and bottom edges collapse symmetrically.

*Earlier attempt was a triangle (taper to point) — corrected to a uniform-width column that shrinks over time.*

### Fix 6: Moonfire DoT zig-zag particles

Replaced pulsing blue ring with 8 persistent `_moonfireParticles` in EnemySprite.
Each particle has its own `phase` offset; sinusoidal lateral push `sin(now/160 + phase) * 38` creates desynchronized zig-zag motion. Particles bounce off the body boundary. Lazy-init on first debuff tick, nulled when debuff expires. Size tuned down: r=1.4, alpha=0.45 (small + semi-transparent as requested).

### Fix 7: Tranquility ambient particles

- New `ParticleSystem.tranquilityAmbient(cx, cy, radius)`: 2 green motes per call, strongly upward (vy -38 to -93), slight upward gravity (-12), 0.8–1.3s life, scattered across the full field radius
- `OneShotEffectSystem.tranquilityField` accepts optional `emitFn` callback, called every frame inside the 4s update loop
- `VFXManager` wires the closure: `() => ps.tranquilityAmbient(d.x, d.y, d.radius || 700)`

### Fix 8: Training dummy debuff rendering (bug fix)

**Root cause:** `TrainingDummy.toDTO()` never included `debuffs`. The client received `state.debuffs = undefined` for every dummy, so `_syncDebuffVisuals` bailed immediately every frame — no DoT visuals ever rendered on any training dummy.

**Fix:** Added the same `activeEffects → debuffs` mapping as `ServerEnemy.toDTO()` to the base `TrainingDummy.toDTO()`. All three dummy types share the base class, so all are fixed.

## Key Learnings

- `TrainingDummy.toDTO()` is a separate codepath from `ServerEnemy.toDTO()` — always check both when adding new state fields that both enemy types need to broadcast
- `OneShotEffectSystem` entries support optional callbacks in their update closure — `emitFn?.()` pattern is clean for per-frame ambient emission tied to a timed effect
- Persistent per-sprite particle state (zig-zag Moonfire dots) lives on the sprite itself, initialized lazily; must be nulled on debuff expiry to avoid stale state
