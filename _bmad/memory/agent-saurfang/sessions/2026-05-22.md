### Shield Ability Rework — Warrior Shield Block + Paladin Divine Protection

**Context:** Both shield abilities required a finger to be held on the button at all times, preventing simultaneous use of other abilities.

**New mechanic implemented:**
- While holding: shield aims freely (unchanged behavior)
- After holding `chargeDuration` ms: fully charged — releasing auto-latches shield in place for `duration` ms
- While auto-latched: player's finger is free for other abilities
- On latch expiry: shield fades, cooldown begins
- If held past full charge: continues working as before (manual hold, no auto-latch until release)

## Session — Projectile hit detection oval hitbox fix

**Context:** Projectiles vs enemies used `circlesOverlap` with `e.radius` — ignoring the oval hitbox (`radiusX = radius/2, radiusY = radius`) that all `ServerEnemy` instances define. Horizontal shots registered hits before the projectile visually reached the enemy's narrow edge.

**Root cause:** `_tickProjectiles` collision check built `enemyCircle = { radius: e.radius }` and called `circlesOverlap`. `ServerEnemy` already had `radiusX`/`radiusY` (used correctly by AOE zone checks and melee), but the projectile path never used them.

**`TrainingDummy` secondary issue:** Had no `radiusX`/`radiusY` at all. Switching to `ellipseCircleOverlap` without a fallback made `e.radiusX` = `undefined` → NaN in the division → `NaN <= 1` = false → total collision failure.

**Fixes:**
- `SkillSystem._tickProjectiles`: `enemyCircle` → `enemyEllipse = { rx: e.radiusX ?? e.radius, ry: e.radiusY ?? e.radius }` + `ellipseCircleOverlap`
- `TrainingDummy`: added `this.radiusX = this.radius / 2` and `this.radiusY = this.radius`

**Pattern:** Any entity in `gs.enemies` that doesn't extend `ServerEnemy` won't have `radiusX`/`radiusY` unless explicitly added. Always use `?? e.radius` fallback and add the fields to new entity classes.

## Key Decisions

- Early release triggers cooldown immediately (no penalty removed — avoids spam exploit)
- Cooldown deferred on auto-latch — server emits it when the tick expires the shield
- Shield angle locked on auto-latch via `shieldExpiresAt == null` guard in INPUT_AIM handler
- Charge progress is client-derived (smooth, zero-latency) from server timestamp

- Deferred cooldown pattern: server can defer COOLDOWN emit to a future tick; check this pattern for any future "delayed activation" ability types

## Session — Training Grounds fade-out transition

**What happened:** Vol'jin's portal entrance end sound was misaligned because Training Grounds had no fade-out — the scene switched instantly, then BattleRenderer faded in. The sound fired after the visual switch.

**Key outcomes:**
- Added `startFadeOut(durationMs, onComplete)` to `TrainingGroundsRenderer` — a full-screen black overlay in `_uiRoot` (last child, above all UI), alpha driven in `_updateUI` tick
- In `main.js` SCENE_CHANGE handler: when transitioning from `trainingGrounds` to `battle`/`bossFight`, fires `audio.handlePortalEntranceEnd()` immediately, then defers `switchScene` to the fade callback (600ms)
- Portal entrance end SFX detection removed from STATE_DELTA (was unreliable — SCENE_CHANGE fires before STATE_DELTA in the same server tick, so `levelZoneState` was already null when STATE_DELTA arrived)

**Root cause of the original timing problem:** `_startCampaign()` is called synchronously inside `_tickZoneSelector()` which changes `this.scene` to `'battle'` before `buildDeltaState()` runs. So the STATE_DELTA that contains `levelZoneState: null` is built with `scene === 'battle'`, and `StateSerializer` returns null. The client never sees `committedIndex` transition — it jumps straight from pending to null.

**Observations:** The 600ms fade window gives the portal end SFX time to play before the battle renderer enters.
